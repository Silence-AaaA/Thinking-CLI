# ADR-011: History Compressor 设计

> Phase 4 | 状态：已实现

## 背景

对话越长，LLM 的注意力越分散，token 消耗也越大。10 轮对话可能已经消耗 30k token，但第 1 轮的工具调用细节对当前决策可能已经没用了。

需要一种机制把早期对话压缩，只保留最近的完整对话。

## 决策 1：规则压缩，不用 LLM

两种方案：

| 方案 | 优点 | 缺点 |
|------|------|------|
| LLM 压缩 | 摘要质量高、自然语言流畅 | 慢（1-2 秒）、贵（消耗 token）、不可预测 |
| 规则压缩 | 快（毫秒级）、免费、可预测 | 摘要质量一般、是结构化文本不是自然语言 |

**选择规则压缩**，原因：
1. 学习项目阶段，规则压缩足够
2. 压缩发生在每轮 LLM 调用之前，不能引入额外延迟
3. 规则压缩的输出格式固定，LLM 容易理解

## 决策 2：按轮次分割，不是按消息数

```
轮次 1: user → assistant → tool → assistant
轮次 2: user → assistant → tool → assistant
...
轮次 N-2: [压缩为摘要]
轮次 N-1: [完整保留]
轮次 N:   [完整保留]
```

**为什么不按消息数分割？（比如"保留最近 20 条消息"）**
- 一轮对话可能有 1 条消息（纯文字回复），也可能有 10 条（多次工具调用）
- 按消息数分割可能把一轮对话切成两半，破坏上下文完整性
- 按轮次分割保证每轮对话的完整性

## 决策 3：压缩内容提取策略

每轮对话提取：
- 用户输入：前 100 字符
- 助手调用的工具名列表
- 工具结果的第一行（前 100 字符）
- 助手的最终回复：前 150 字符

**为什么不提取更多？**
- 压缩的目的是"知道之前做了什么"，不是"重现之前的过程"
- 100-150 字符足够表达一轮对话的核心
